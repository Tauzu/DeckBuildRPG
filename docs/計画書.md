# デッキビルドRPG 開発計画書

> 本書は「企画書.md」の内容を実装するための開発計画です。
> 前提：**個人開発（1人）**、作業時間は **週10～15時間程度** と仮定しています。体制が違う場合は期間を見直してください。

---

## 1. 目的とゴール

| 項目 | 内容 |
|---|---|
| 目的 | 企画書のゲーム「辺境村の英雄たち（仮）」をブラウザで遊べる形にして公開する |
| 最終ゴール | 1～4人のオンライン協力プレイができる版を公開する |
| 中間ゴール | ソロプレイで最初から最後まで遊べる版を作り、ルールの面白さを確認する |

### 方針
- **面白さの確認を最優先する**。見た目より先に、ルールが動く最小限の版を作ってテストプレイする。
- **ゲームのルール部分と画面を分けて作る**。ルール部分はサーバーとブラウザの両方で使い回せるようにする。
- **カードの数値はデータファイルで管理する**。プログラムを書き換えずにバランス調整できるようにする。

---

## 2. 技術構成

| 項目 | 採用技術 | 理由 |
|---|---|---|
| 言語 | TypeScript | サーバーとブラウザで同じコードを共有できる |
| 画面 | React + Vite | カードゲームのUIは画面部品の組み合わせで作りやすい |
| 通信 | WebSocket（Socket.IO） | ルーム制のリアルタイム同期を手軽に作れる |
| サーバー | Node.js | ルール部分のコードをそのまま使える |
| カードデータ | JSON | 数値の調整がしやすい |
| テスト | Vitest | ルール部分の自動テスト |
| 公開先 | 未定（候補：Render / Fly.io などWebSocketが使えるサービス） | |

### コードの構成

```
DeckBuildRPG/
├─ packages/
│  ├─ core/     … ゲームのルール（画面や通信に依存しない）
│  ├─ client/   … ブラウザの画面
│  └─ server/   … マルチプレイ用サーバー
└─ data/        … カードデータ（JSON）
```

- `core` は「今のゲーム状態」と「プレイヤーの操作」を受け取って「次のゲーム状態」を返す作りにする。
  ソロプレイではブラウザ内で、マルチプレイではサーバーで同じ `core` を動かす。

## 3. 開発フェーズ

| フェーズ | 内容 | 期間の目安 | 完了の条件 |
|---|---|---|---|
| 0. 紙での試遊 | 紙のカードで企画書のルールを遊んでみる | 1週 | 1人で最後まで遊び、大きな問題がないことを確認 |
| 1. ルール実装 | `core` にゲームのルールを作る | 3週 | 自動テストでソロの1ゲームを最後まで進められる |
| 2. ソロ版 | 最低限の画面を作り、ブラウザでソロプレイできるようにする | 3週 | ブラウザで最初から勝敗まで遊べる |
| 3. バランス調整 | テストプレイと数値の調整を繰り返す | 2週 | 勝率がおよそ40～60%に収まる |
| 4. ステージ制 | チュートリアル、ステージ選択、ステージごとのカード・ボス、進み具合の保存 | 4週 | チュートリアルからステージ4まで1人で通して遊べる |
| 5. マルチプレイ | サーバー、ルーム、手番の同期を作る | 4週 | 4人で最後まで遊べる |
| 6. 見た目の強化 | カードの絵、アニメーション、効果音 | 3週 | 初めての人が説明なしで操作できる |
| 7. 公開準備 | 公開、遊び方の説明、外部の人によるテストプレイ | 2週 | URLを共有して誰でも遊べる |

**合計：約22週（5～6か月）**

## 4. フェーズごとの作業内容

### フェーズ0：紙での試遊
- [ ] 企画書のカードを紙に書き出す（または表計算ソフトで印刷）
- [ ] ソロで3回以上遊ぶ
- [ ] 2人で1回以上遊ぶ（手番ごとの進軍のペースを確認）
- [ ] 気づいた点を企画書に反映する

紙で遊ぶとプログラムを書かずにルールの問題が見つかるため、最初に行う。

### フェーズ1：ルール実装（`core`）
- [ ] プロジェクトの土台を作る（TypeScript、Vitest、フォルダ構成）
- [ ] カードデータの形式を決め、企画書のカードをJSONにする
- [ ] ゲーム状態の型を作る（デッキ、手札、捨て札、進軍ルート、集落の耐久値、経験値）
- [ ] 山札を引く・シャッフルする（乱数は固定できるようにし、テストで同じ結果を再現できるようにする）
- [ ] 集落を訪れる：村効果、購入、レベルアップ、転職
- [ ] 敵を倒す：ダメージ計算、耐性、武器の装備、食糧値による制限
- [ ] 敵の進軍：移動、公開、集落への到達、妨害能力
- [ ] 敵の山札の作成（序盤の束・終盤の束・ボス）
- [ ] 勝ち負けの判定
- [ ] 自動テスト（ルールごとのテスト、1ゲームを最後まで進めるテスト）

### フェーズ2：ソロ版
- [ ] 画面の構成を決める（進軍ルート、村の在庫、手札、情報欄）
- [ ] カードの表示部品
- [ ] 手札から場にカードを出す操作（クリックで選ぶ方式から始める）
- [ ] 「集落を訪れる」「敵を倒す」の選択と実行
- [ ] 敵の進軍の表示
- [ ] 勝敗画面と評価の表示
- [ ] ゲームの記録（どの手番で何をしたか）を残す仕組み（バランス調整に使う）

### フェーズ3：バランス調整
- [ ] 簡単な自動プレイ（コンピューターが決まった方針で遊ぶ）を作り、何百回も試して勝率を調べる
- [ ] 企画書の「テストプレイで確認すること」を1つずつ確認する
  - 敵の進軍速度と撃破ペース
  - 盗賊・吟遊詩人の村効果の強さ
  - 倒した敵カードによるデッキの圧迫
  - ボスの生命力
- [ ] 調整した数値を企画書に反映する

### フェーズ4：ステージ制（企画書 12章）
- [ ] ステージのデータ形式を決める（登場する英雄・食料・武器・敵、ボス、人数ごとの数値）
- [ ] `core` がステージのデータからゲームを準備できるようにする
- [ ] ステージ1〜3のボスを作る（チュートリアル用の小さなボスも）
- [ ] 自動プレイでステージごとの勝率を目安に合わせる
- [ ] ステージ選択の画面と、進み具合の保存（ブラウザに保存）
- [ ] チュートリアル（カードの並びを固定し、画面の案内に従って1つずつ体験する）
- [ ] 1人でチュートリアルからステージ4まで通して遊ぶ

### フェーズ5：マルチプレイ
- [ ] サーバーの土台（Socket.IO）
- [ ] ルームの作成・参加（ルームコードを共有する方式）
- [ ] 手番の管理と状態の同期（ゲーム状態はサーバーだけが持ち、ブラウザは操作を送るだけにする）
- [ ] 人数ごとの調整（敵の山札の枚数、耐久値、ボスの生命力）
- [ ] 通信が切れたときの再接続
- [ ] MVP・称号の表示
- [ ] 部屋を作った人が、解放済みのステージから選ぶ。クリアしたら参加者全員の進み具合に反映する
- [ ] 2～4人でのテストプレイ

### フェーズ6：見た目の強化
- [ ] カードの絵（自作 または 利用条件を確認した素材）
- [ ] カードを出す・敵が進むなどのアニメーション
- [ ] 効果音・BGM
- [ ] 遊び方の説明（ルール画面。チュートリアルはフェーズ4）
- [ ] スマートフォンでの表示確認

### フェーズ7：公開準備
- [ ] 公開先を決めてデプロイする
- [ ] 外部の人にテストプレイしてもらい、意見を集める
- [ ] 不具合の修正
- [ ] 公開

## 5. マイルストーン

| 時期（目安） | マイルストーン | 確認すること |
|---|---|---|
| 1週目の終わり | 紙での試遊が完了 | ルールに大きな問題がないか |
| 4週目の終わり | ルールが自動テストで動く | 企画書のルールがすべて実装されているか |
| 7週目の終わり | **ソロ版が遊べる** | 遊んで面白いか（ここで面白くなければルールを見直す） |
| 9週目の終わり | バランス調整が完了 | 勝率、プレイ時間（ソロで20分前後） |
| 13週目の終わり | **ステージ制が遊べる** | チュートリアルで迷わないか、ステージを進めたくなるか |
| 17週目の終わり | **マルチプレイが遊べる** | 4人で最後まで遊べるか、待ち時間が長すぎないか |
| 20週目の終わり | 見た目の強化が完了 | 初めての人が迷わず遊べるか |
| 22週目の終わり | **公開** | |

7週目の「ソロ版」の時点で面白さを判断し、続けるか、ルールを見直すかを決める。

## 6. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| 遊んでみて面白くない | 作り直しが必要になる | 紙での試遊とソロ版で早めに確認する。マルチプレイや見た目に手を付ける前に判断する |
| バランス調整に時間がかかる | 公開が遅れる | 自動プレイで大量に試す。数値はJSONで管理し、すぐ変えられるようにする |
| マルチプレイの同期で不具合が出る | 遊べない状態になる | ゲーム状態はサーバーだけが持つ。ルールは `core` にまとめ、ソロ版で十分テストしておく |
| 他の人の手番の待ち時間が長い | 遊んでいて退屈になる | 他の人の手番中も操作が見えるようにする。1手番に制限時間（例：90秒）を付けることを検討する |
| カードの絵の用意が負担になる | 見た目の強化が遅れる | 最初は文字とアイコンだけのカードで進める。絵は最後に差し替える |
| 作業時間が確保できない | 全体が遅れる | フェーズごとに区切りを付け、ソロ版だけでも先に公開できるようにする |

## 7. 今回の対象外（将来の候補）

- アカウント登録・ランキング
- 知らない人とのマッチング（今回はルームコードを共有する方式のみ）
- ステージ4より先のステージ（新しい英雄・敵・ボスが必要）
- スマートフォン専用の操作
